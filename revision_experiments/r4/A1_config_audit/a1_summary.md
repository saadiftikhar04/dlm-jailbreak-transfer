# A1 configuration audit, interim C0 result

`config_matrix.csv` contains all 18 attack-victim cells and is generated by `build_a1_tables.py` from the existing authoritative decoding matrix plus the pinned checkpoint map. `judge_matrix.csv` separates the attack-specific labels from the common judges. `a1_source_hashes.json` records the exact local source snapshots used for this audit. The tables contain no prompt or response text.

## Verified configuration differences

- The victim generation cap is 512 tokens and the inspected target paths truncate the input at 2,048 tokens. Causal decoding is sampled, with PiF/ArrAttack at temperature 0.8 and top-p 0.9, and MetaCipher at temperature 0.7 and top-p 0.9.
- LLaDA differs fourfold by attack: PiF uses `steps=gen_length` with 128-token blocks, which is 128 steps per block at the 512-token cap; MetaCipher and ArrAttack use 128 total steps over four blocks, or 32 per block.
- Dream uses origin remasking at temperature 0 for PiF/ArrAttack, but entropy remasking at temperature 0.2 and 128 steps for MetaCipher. DiffuCoder uses entropy remasking at temperature 0.3 with steps proportional to generated length for PiF/ArrAttack, versus temperature 0.4 and 128 steps for MetaCipher.
- The plan's assumption that the other victims already share one configuration across attacks is false: the three causal victims differ in temperature between MetaCipher and PiF/ArrAttack, and Dream and DiffuCoder differ in algorithm, temperature, or step schedule under MetaCipher. Only G4 is currently specified to standardize LLaDA; the remaining as-run conflicts must be represented as design limitations unless a separate matched rerun is approved.
- The Llama cells are mixed identities by design of the recorded runs: PiF and MetaCipher use Llama-3.2-3B; ArrAttack uses Llama-3.1-8B. The held-out ArrAttack runtime log confirms the 3.1-8B model. The current local `ArrAttack/utils/model_utils.py` registry differs, so its current source cannot be treated as the run-time identity evidence.
- The inspected attack-specific judges are not one shared instrument. PiF’s semantic judge is DeepSeek API; MetaCipher’s categorical judge is DeepSeek API; ArrAttack’s saved three-way `gpt_fuzz` source is not recoverable from the retained code and rows. Local code contains both a GPTFuzz classifier and a DeepSeek auxiliary score, but neither by itself reproduces the saved three-way field. The label-to-success mapping is recoverable: only `compliance` counts as success.
- PiF uses up to 50 victim queries inside its prompt-optimization loop and stops on a rejection-prefix heuristic. For DLM victims, `run_pif.py` then issues a separate `target_generate` call on the selected final prompt and overwrites the optimizer response in the saved row. The stored `total_query` field excludes this additional DLM call.
- Additional first-query configuration audit for the D2 Llama-3.1 rerun: PiF's causal optimizer feedback call in `attack_mlm.py` uses `tokenizer.apply_chat_template` without explicitly setting `add_generation_prompt`, so the tokenizer's default omits the assistant-generation suffix; it truncates at `max_length=128` and calls `model.generate(..., max_length=512)` without an attention mask, pad-token or end-token override. The pinned Llama-3.1 `generation_config.json` therefore supplies `do_sample=true`, temperature 0.6, top-p 0.9 and the three EOS token IDs for this first victim response. This differs from the later PiF final-response helper configuration (assistant-generation suffix present, temperature 0.8, top-p 0.9, input cap 2,048 and 512 new tokens). The matching Llama-3.1 plaintext controls include this first-feedback decoder as a separate condition; it is not interchangeable with the final-response control.
- The pinned tokenizer preflight over the exact 913-row canonical pool found one prompt above this 128-token input cap with the source's default template behavior. It is intentionally truncated by the source PiF feedback path; the matching control uses the same token IDs and truncation. Machine-readable values and source/config hashes are in `a1_pif_feedback_query_config.csv`.
- No explicit victim-generation seed is set in the checked target-generation entrypoints. The seed used for each historical run is not present in the judged rows and must be recorded as unknown, not inferred.
